## Detailed Findings

### BUG-001: HP Clamping Inconsistency
- **File:** `src/core/models/Unit.ts` (L72), `src/core/validation/battleStateInvariants.ts` (L100)
- **Description:** `calculateMaxHp` only accounts for base stats and level scaling. It ignores HP bonuses from equipment (e.g., Armor with +HP) and status effects. Since this function is used to clamp HP in `applyDamage`, `applyHealing`, and `checkAutoRevive`, units with HP-boosting gear will have their extra HP stripped away the moment they take damage or receive healing.
- **Severity:** Medium/High

### BUG-002: AoE Damage Reporting
- **File:** `src/core/services/BattleService.ts` (L195)
- **Description:** In `performAction`, when an ability deals damage, the `hit` event is emitted for each target. However, the `amount` passed to each event is the `result.damage` from `executeAbility`, which is the *summed total* damage dealt to ALL targets.
- **Impact:** An AoE that hits 4 targets for 25 damage each will show "100" damage above every target's head in the UI.
- **Reproduction steps:** 1) Start a battle with at least 3 enemies. 2) Use a multi-target AoE ability (e.g., Fire-all) that deals a fixed per-target amount. 3) Observe floating damage numbers above each target; they display the summed total instead of per-target damage.
- **Severity:** High

### BUG-003: Non-Functional Mana Generation
- **File:** `src/core/services/QueueBattleService.ts` (L335, L480)
- **Description:** Basic attacks generate 1 mana during the `executing` phase and add it to `remainingMana`. However, at the end of the round, `transitionToPlanningPhase` calls `refreshMana`, which resets `remainingMana` to `maxMana`. 
- **Impact:** Since mana can only be spent during the `planning` phase, and it resets to max before every planning phase, any mana generated by basic attacks is effectively deleted before it can be used.
- **Reproduction steps:** 1) Begin a battle with a player party that has less than max mana. 2) Queue and execute a basic attack that grants +1 mana during execution. 3) After the round ends, verify that `remainingMana` is equal to `maxMana` and the 1 mana gain is not persistent (no usable extra mana in planning).
- **Severity:** High

### BUG-004: UI State De-sync
- **File:** `src/ui/state/queueBattleSlice.ts` (L240), `src/ui/components/QueueBattleView.tsx`
- **Description:** `executeQueuedRound` updates the `battle` state in the store to the state *after* the entire round has finished. Meanwhile, the UI processes the `events` queue one by one with delays for animations. 
- **Impact:** Components that read HP directly from `battle.playerTeam.units` (like portrait bars) will jump to their final values (e.g., 0 HP) immediately when the "Execute" button is pressed, even if the killing blow animation hasn't played yet.
- **Severity:** Medium

### BUG-005: AI AoE Overkill Restriction
- **File:** `src/core/services/AIService.ts` (L178)
- **Description:** The `selectTargets` function for the `weakest` case (the default) contains an `avoidOverkill` check. If this check passes, it returns `[nonOverkill[0]!.target.id]`, which is a single-element array.
- **Impact:** If an AI uses an AoE ability (like `all-enemies`) that has the `avoidOverkill` hint, it will only target a single unit instead of the entire team.
- **Severity:** Medium

### BUG-006: AI Ignores Debuffs
- **File:** `src/core/services/AIService.ts` (L118)
- **Description:** The `scoreAbility` function calculates the utility of buff/debuff abilities. It currently only checks `ability.buffEffect` and ignores `ability.debuffEffect`.
- **Impact:** Abilities that only apply debuffs (like "Weaken DEF") will be given a utility score of 0, making the AI almost never choose them over basic attacks or other skills.
- **Severity:** Medium

### BUG-007: Summon Healing Revive
- **File:** `src/core/services/QueueBattleService.ts` (L590)
- **Description:** `executeDjinnSummons` processes healing summon effects by mapping over all units and adding HP. It uses `Math.min(unit.currentHp + healAmount, maxHp)` without checking if the unit is alive.
- **Impact:** Summons with healing effects will unintentionally revive KO'd party members. While this might be a design choice, it is inconsistent with the `applyHealing` algorithm which requires an explicit `revivesFallen` flag.
- **Severity:** Medium

### BUG-008: Tower Reward Roster Cap
- **File:** `src/ui/state/towerSlice.ts` (L380)
- **Description:** `grantTowerMilestoneRewards` loops through rewards and checks `state.roster.length >= 10`. If true, it breaks the loop and stops adding units.
- **Impact:** If a reward contains multiple units, and the player already has some of them, the roster check might block adding a *new* unit just because the total roster count is 10, even if the preceding items in the reward list were skipped as duplicates.
- **Severity:** Low

### BUG-009: New Djinn Highlighting
- **File:** `src/ui/state/rewardsSlice.ts` (L55)
- **Description:** `processVictory` calculates `newDjinnIds` by comparing `team.collectedDjinn` (current store state) with `battle.playerTeam.collectedDjinn`. 
- **Impact:** If a Djinn was added as a battle reward by the service, it won't be in the store's `team` yet (as `updateTeam` is called later). Thus `newDjinnIds` will be empty, and the Rewards screen won't show the "New!" badge for earned Djinn.
- **Severity:** Low

### BUG-010: Unstable Turn Order Tie-break
- **File:** `src/core/algorithms/turn-order.ts` (L50)
- **Description:** The deterministic tie-breaker uses `tieRng.next()` for each unit in ID order. If a unit dies, it is removed from `aliveUnits`, changing the sequence of RNG calls for all subsequent units.
- **Impact:** The relative turn order of two units might swap simply because an unrelated third unit was KO'd, which can feel erratic to players.
- **Severity:** Low

### BUG-011: Revival Target Filtering
- **File:** `src/core/algorithms/targeting.ts` (L24, L82)
- **Description:** `resolveTargets` and `getValidTargets` always filter out KO'd units using `!isUnitKO(u)`. 
- **Impact:** Even if an ability has `revive: true` or `revivesFallen: true`, the targeting logic prevents it from ever being cast on a KO'd unit, making revival mechanics non-functional.
- **Reproduction steps:** 1) Create or load a battle where a party member is KO'd. 2) Attempt to cast a revival spell/ability (revivesFallen: true) from a unit with that action available. 3) Observe that KO'd allies are not selectable in the targeting UI and ability fails to target them.
- **Severity:** Critical

### BUG-012: Immunity Blocks Positive Effects
- **File:** `src/core/algorithms/status.ts` (L145)
- **Description:** `applyStatusToUnit` checks `isImmuneToStatus(unit, newStatus.type)`. If a unit has a status with `all: true` immunity, `isImmuneToStatus` returns true for ANY status type.
- **Impact:** Units with "all" status immunity (e.g., from a powerful protective spell) cannot be buffed or healed over time, as these positive statuses are also blocked.
- **Reproduction steps:** 1) Give a unit an "all" immunity status (via debug or item). 2) Attempt to apply a positive status (buff or regen) or a heal-over-time ability. 3) Observe the status/heal is rejected and no UI status-applied event appears.
- **Severity:** High

### BUG-013: Equipment Elemental Resistance Ignored
- **File:** `src/core/services/BattleService.ts` (L550)
- **Description:** `calculatePsynergyDamage` only checks `defender.equipment.armor?.elementalResist`. It ignores resistances from helmets, boots, and accessories. Furthermore, `calculatePhysicalDamage` does not check for equipment elemental resistance at all, even for elemental physical attacks.
- **Impact:** High-tier equipment with elemental resists (except armor in specific cases) is non-functional for damage reduction.
- **Reproduction steps:** 1) Equip a defender with a helmet or accessory that grants elemental resistance (e.g., +30% fire resist). 2) Deal elemental physical or psynergy damage and compare damage with and without the item equipped. 3) Observe that the resistance is not applied and damage remains unchanged.
- **Severity:** High

### BUG-014: Missing Status Events
- **File:** `src/core/services/BattleService.ts` (L245)
- **Description:** `performAction` only emits `status-applied` events if `ability.statusEffect` is present. It misses statuses applied via `ability.debuffEffect` and `ability.buffEffect`. Additionally, it only emits events for "new" status types, so refreshing an existing status doesn't trigger UI feedback.
- **Impact:** Debuffs and repeated status applications are "silent" in the UI (no animations or log events), leading to player confusion.
- **Severity:** Medium

## Changes made 2026-01-06 (this audit)

Small, targeted fixes applied to address correctness issues discovered during the audit below.

1) Fix: encounter-finished emitted with post-action state
   - File modified: src/ui/state/battleSlice.ts
   - Problem: encounter-finished events were built using the pre-action battle state which could omit or misreport the encounterId.
   - Resolution: use getEncounterId(result.value.state) (the post-action state) when creating encounter-finished; this ensures story slice notifications reflect the actual ended battle.

2) Fix: preview() edge cases and sample count
   - File modified: src/ui/state/battleSlice.ts
   - Problems: preview used a hard-coded sample count (16) and returned min as Infinity if all trials failed.
   - Resolution: preview now uses PREVIEW_SAMPLES and tracks successful samples; returns safe defaults {avg:0,min:0,max:0} if no previews succeed.

Files changed in this pass
- src/ui/state/battleSlice.ts (minor fixes described above)

## Additional Findings (2026-01-06 audit pass 2)

1) queuedActions / team size edge cases
- Files: src/core/models/BattleState.ts, src/core/services/QueueBattleService.ts, src/core/validation/battleStateInvariants.ts, src/ui/state/queueBattleSlice.ts
- Description: Multiple places assume queuedActions length equals team size and adjust the array (pad/truncate) when sizes differ. If team composition changes mid-battle (summons, recruitment, or unit death/resurrection), queuedActions may be trimmed or re-indexed, causing queued actions to shift between units or be lost.
- Reproduction steps: 1) Start a battle with 3-player team. 2) Queue actions for all units. 3) During execution, add/remove a unit (simulate by a summon or forced roster change) or revive a unit mid-round and observe queuedActions mapping after transitionToPlanningPhase; if actions are missing or assigned to wrong units, issue reproduces.
- Severity: High

2) queuedActions null-handling inconsistencies
- Files: src/core/services/QueueBattleService.ts, src/core/algorithms/mana.ts, src/ui/components/QueueBattleView.tsx
- Description: Some algorithms filter null entries (aliveUnitActions) while UI components and mana calculations assume non-null entries in certain places, causing potential runtime errors or incorrect mana totals when nulls are present for dead units.
- Reproduction steps: 1) KO a unit in the middle of queueing. 2) Inspect QueueBattleView mana totals and try to interact with the queue UI; if NaN/undefined or mismatched totals appear, the issue reproduces.
- Severity: Medium

3) OverworldV2 player layer / double-render risk
- Files: src/ui/components/overworld/layers/InteriorFurnitureLayer.ts, src/ui/components/overworld-v2/OverworldV2.tsx
- Description: OverworldV2 provides its own PlayerLayer and some legacy layers disable their player drawing with comments. This mixed rendering approach risks double-rendering or missing draw-order/invalidation when swapping between V1/V2 components during transitions (e.g., entering/exiting interiors).
- Reproduction steps: 1) Enter an interior using OverworldV2 active. 2) Trigger a map transition that swaps layers (enter/exit). 3) Observe sprite/player draw glitches or z-order flicker; if double-drawing or missing player sprite occurs, issue reproduces.
- Severity: Medium

4) Zod BattleState schema strictness vs runtime adjustments
- Files: src/data/schemas/BattleStateSchema.ts, src/ui/state/queueBattleSlice.ts
- Description: Zod schema enforces queuedActions length min/max relative to constants; runtime code adjusts queuedActions length dynamically which can produce states that pass runtime adjustments but fail schema validation on serialization/deserialization boundaries.
- Reproduction steps: 1) Create a battle state object in-memory then programmatically mutate team size and queuedActions length without using store helpers. 2) Attempt to persist/validate via schema; if validation fails despite runtime code having adjusted arrays, the mismatch reproduces.
- Severity: Low/Medium

These additions are recorded to ensure triage includes queue/queuedActions stability and overworld render transition risks alongside the previously listed critical bugs. Prioritize queuedActions/team-size issues as part of the P0/P1 list.


## AUDIT: Round 1 (2026-01-06T19:32:07Z) — Initial findings

Summary: Automated scan of state slices, queue/battle code, and overworld/input subsystems. These are prioritized for follow-up debugging and reproducible tests.

1) queuedActions / Battle queue invariants (Severity: P1)
- Finding: queuedActions is central to battle flow and is validated in schemas (data/schemas/BattleStateSchema.ts) and services, but multiple UI components directly index into battle.queuedActions (ActionBar, BattleActionMenu, QueueBattleView). There are places that copy/trim or regenerate the queue (queueBattleSlice, QueueBattleService).
- Risk: race or mismatch when team size changes (KO, revive) can produce index errors or stale actions remaining after team updates.
- Repro steps:
  1. Start battle with full party (4 units).
  2. Queue actions for each slot, then KO a unit (enemy attack) reducing team size or change party via service that regenerates queue.
  3. Observe UI components and console for out-of-bounds access or mismatched UI state.
- Suggested triage: add defensive guards in UI accessors and a canonical single-source-of-truth reset path that clears queuedActions on encounter end or team size change.

2) Revival targeting / target filtering (Severity: P0 referenced)
- Finding: BUG-011 in current report notes revival abilities cannot target KO'd units due to filtering logic. Confirmed presence in targeting code paths used by QueueBattleService and validation layers.
- Repro steps: Use a revival Ability on a KO'd ally; confirm target list excludes KO'd units.
- Suggested triage: fix target filtering to allow 'revive' type effects to include KO'd units while maintaining other filters.

3) InputLock / scene-scoped locks (Severity: P2)
- Finding: InputLock implementation is reference-counted and supports scoped locks (game/systems/InputLock.ts). UI and menu routers wire into InputLock (MenuStackRouter, PauseMenu, SettingsHowToPlayMenu) and OverworldV2 consults gameplay lock before processing input.
- Risk: potential for lingering scoped locks if a scene does not reliably release on error path; could produce permanent input disable until reload.
- Repro steps:
  1. Open Settings/HowToPlay and trigger an error or abrupt unmount (devtools detach) before unlocking.
  2. Attempt normal gameplay input; check inputLock.getLockCount(scene) and whether menus have cleared their handles.
- Suggested triage: add unit tests around scoped lock acquire/release and instrument logging on register/unregister to detect leaks.

4) OverworldV2 input gating (Severity: P2)
- Finding: OverworldV2 gates input using modeRef and activeModalRef. There are early-return checks in key handlers; ensure no path sets mode but forgets to update refs causing input to be dropped.
- Repro steps: Rapidly transition scenes (menu open -> close -> immediate map change) and assert input responsiveness.
- Suggested triage: add e2e test for rapid scene transitions and ensure input enabled state is deterministic.

Next steps:
- Triage P0/P1 items with unit/e2e tests that reproduce the conditions.
- Instrument battle end and team-size-change paths to enforce a canonical queue reset.
- Run targeted tests around InputLock scoped acquisition/release.
